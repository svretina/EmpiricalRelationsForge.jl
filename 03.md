# Regression libraries in Julia: what should EmpiricalRelationsForge.jl use?

After reviewing the current Julia ecosystem, I recommend reusing established numerical solvers and implementing our own lightweight scientific regression interface.

In particular, two libraries stand out:

- CurveFit.jl — a unified interface for linear, polynomial, nonlinear, and specialized curve fitting.
- NonlinearSolve.jl — a more flexible numerical backend for nonlinear least squares, including Gauss–Newton, Levenberg–Marquardt, trust-region methods, and bounded problems.

A third library, SymbolicRegression.jl, should remain our dedicated engine for discovering previously unknown functional forms.

The key insight is that many of the published BNS postmerger relations are nonlinear in the input variables but linear in their fitted coefficients. Such relations do not require nonlinear optimization at all.

## 2. Why most of our published relations don't need nonlinear optimization

Consider the type of relation used in the BNS postmerger literature:

\\[ f\_{\rm peak}M\_{\rm chirp} =a_0+a_1M\_{\rm chirp} +a_2\tilde\Lambda^{-1/2}. \\]

Although \\(\tilde\Lambda^{-1/2}\\) is nonlinear in tidal deformability, the unknown coefficients \\(a_0,a_1,a_2\\) enter linearly.

Define

\\[ y_i=f\_{{\rm peak},i}M\_{{\rm chirp},i} \\]

and the design matrix

\\[ X= \begin{pmatrix} 1&M\_{{\rm chirp},1}&\tilde\Lambda_1^{-1/2}\\\ 1&M\_{{\rm chirp},2}&\tilde\Lambda_2^{-1/2}\\\ \vdots&\vdots&\vdots\\\ 1&M\_{{\rm chirp},N}&\tilde\Lambda_N^{-1/2} \end{pmatrix}. \\]

Then the regression problem is simply

\\[ \min\_{\boldsymbol a}\\|X\boldsymbol a-\boldsymbol y\\|\_2^2. \\]

In Julia:

```
using LinearAlgebra

X = hcat(
    ones(length(M_chirp)),
    M_chirp,
    Lambda_tilde .^ (-0.5)
)

y = f_peak .* M_chirp

coefficients = X \ y
```

This is already a numerically sound least-squares solution using Julia's standard linear algebra.

For the scale of our BNS database, with potentially hundreds or thousands of measurements and perhaps 3–20 coefficients, there is little reason to depend on a general nonlinear fitting package for this class of problems.

The real engineering challenge is constructing the correct basis functions and target transformations.

### A more general example

Suppose we want to investigate

\\[ f\_{\rm peak} =a_0+a_1M\_{\rm chirp} +a_2\tilde\Lambda^{-1/2} +a_3M\_{\rm chirp}\tilde\Lambda^{-1/2} +a_4\tilde\Lambda^{-1}. \\]

We can construct a feature library containing

\\[ \left\\{ 1,\\, M\_{\rm chirp},\\, \tilde\Lambda^{-1/2},\\, M\_{\rm chirp}\tilde\Lambda^{-1/2},\\, \tilde\Lambda^{-1} \right\\}. \\]

All coefficients remain linear.

This suggests implementing a small, general-purpose basis-function regression engine using `LinearAlgebra`, rather than writing a separate fitting routine for every functional form.

## 3. When do we actually need nonlinear least squares?

Suppose symbolic regression suggests

\\[ f\_{\rm peak} =a_0+a_1M\_{\rm chirp}^{a_2} \tilde\Lambda^{a_3}. \\]

Now \\(a_2\\) and \\(a_3\\) are unknown exponents. The coefficients enter nonlinearly, so ordinary linear least squares is no longer sufficient.

We want to solve

\\[ \min\_{\boldsymbol a} \sum\_{i=1}^{N} w_i\left[ F(\boldsymbol x_i;\boldsymbol a)-y_i \right]^2. \\]

For this, I favor `NonlinearSolve.jl`.

Its nonlinear least-squares interface supports a polyalgorithm combining Gauss–Newton with Levenberg–Marquardt and trust-region fallbacks, and it has specialized bounded algorithms. That flexibility is useful when a discovered formula contains nonlinear powers, exponentials, or other difficult parameter dependencies.&#x20;

An alternative is `CurveFit.jl`, which already wraps `NonlinearSolve.jl` for general nonlinear fitting. If its higher-level interface meets our requirements, we should use it instead of recreating the wrapper.

### An important consideration: where we minimize the residual

For our BNS relations, fitting \\(f\_{\rm peak}M\_{\rm chirp}\\) is not generally equivalent to minimizing errors in \\(f\_{\rm peak}\\).

If

\\[ y=M\_{\rm chirp}f\_{\rm peak}, \\]

then minimizing

\\[ \sum_i\left(y_i-\hat y_i\right)^2 \\]

corresponds to minimizing

\\[ \sum_i M\_{{\rm chirp},i}^{2} \left(f\_{{\rm peak},i}-\hat f\_{{\rm peak},i}\right)^2. \\]

Thus the target transformation changes the implicit weighting.

EmpiricalRelationsForge.jl must let researchers explicitly choose the target transformation, loss space, and weighting scheme. This is scientifically more important than choosing between two well-implemented least-squares solvers.

I would keep `CurveFit.jl` as an alternative to benchmark during development, rather than making both it and `NonlinearSolve.jl` mandatory dependencies immediately.

There is another reason to keep the interface independent of the solver: the Forge may eventually perform robust regression, Bayesian inference, constrained fitting, or custom multi-objective optimization. These do not all fit naturally into a single `curve_fit` abstraction.

## 5. What should we implement ourselves?

| Component                              | Implement in Forge?  | Why                                          |
| -------------------------------------- | -------------------- | -------------------------------------------- |
| QR/SVD numerical algorithms            | No                   | Julia already provides them                  |
| Gauss–Newton / Levenberg–Marquardt     | No                   | Use mature solvers                           |
| Polynomial and nonlinear feature basis | Yes                  | Needed for flexible scientific relations     |
| Target transformations                 | Yes                  | Essential for physically meaningful fitting  |
| Weighted residual construction         | Yes                  | Consistent treatment across backends         |
| Parameter constraints and scaling      | Thin adapter         | Pass to solver where supported               |
| Symbolic expression search             | No                   | Use SymbolicRegression.jl                    |
| Cross-validation by EOS                | Yes                  | Specific scientific validation need          |
| Model-complexity comparison            | Yes                  | Common evaluation framework                  |
| Confidence intervals / bootstrapping   | Mostly orchestration | Reuse statistical primitives                 |
| Result export                          | Yes                  | Must interoperate with EmpiricalRelations.jl |
| Formula dimensional checks             | Yes, incrementally   | Protect scientific validity                  |

An especially useful feature would be the ability to define a model using basis functions rather than manually constructing a design matrix each time.

For example, the proposed API could look like:

```
basis = BasisSet(
    :constant,
    :M_chirp,
    :Lambda_tilde => x -> inv(sqrt(x)),
    (:M_chirp, :Lambda_tilde) =>
        (m, λ) -> m / sqrt(λ)
)

result = fit(
    dataset,
    LinearBasisRegression(basis)
)

formula(result)
coefficients(result)
```

This is illustrative API design, not an existing implementation.

For a publishable model, each basis term should additionally have a stable identifier, mathematical representation, units, and a serializable specification. Anonymous closures are useful during exploration but insufficient as the sole representation of a reproducible empirical relation.

# EmpiricalRelationsForge.jl — Regression Backend Decision

## Objective

Use mature Julia numerical libraries wherever possible. Do not implement custom numerical optimization algorithms.

Our own implementation should focus on scientific model construction, basis functions, target transformations, reproducibility, and validation.

## 1. Evaluate existing fitting packages

Inspect the current documented APIs and compatibility of:

- CurveFit.jl
- NonlinearSolve.jl
- LsqFit.jl
- GLM.jl
- SymbolicRegression.jl

Create a short technical comparison using representative regression problems from the BNS postmerger literature.

Prefer stable, documented APIs.

## 2. Primary linear regression backend

Use Julia's LinearAlgebra for models linear in their fitted coefficients.

Implement a generic design-matrix builder that accepts named basis functions.

Use QR by default, with SVD available for ill-conditioned or rank-deficient problems.

Avoid explicitly forming or inverting the normal-equation matrix.

Support:

- Multivariate inputs.
- Polynomial bases.
- Mixed polynomial terms.
- Negative and fractional powers.
- Fixed nonlinear transformations.
- Cross terms.
- Weighted least squares.
- Target transformations.
- Model-rank diagnostics.

Do not require a nonlinear optimizer for models that are linear in their coefficients.

## 3. Nonlinear least-squares backend

Use NonlinearSolve.jl as the primary candidate for general nonlinear parameter estimation.

Construct residual vectors and pass them to its supported nonlinear least-squares interface.

Evaluate:

- Gauss–Newton.
- Levenberg–Marquardt.
- Trust-region methods.
- Bounded fitting.
- Automatic differentiation where compatible.
- Parameter and residual scaling.

Provide a thin abstraction so that the numerical solver can be changed without modifying the public model interface.

Benchmark the equivalent CurveFit.jl interface before committing to a direct NonlinearSolve.jl dependency. If CurveFit covers our requirements cleanly, prefer its higher-level API.

Do not maintain two competing production nonlinear backends in the initial release.

## 4. Symbolic regression

Use SymbolicRegression.jl for discovering mathematical functional forms.

Preserve its Pareto frontier and candidate expression representations.

Allow a discovered symbolic expression to be refitted on the training dataset with an appropriate numerical backend, without changing its mathematical structure.

Record whether coefficients were optimized by symbolic regression, a subsequent least-squares refit, or both.

Evaluate discovered models against the classical baselines.

## 5. Scientific model specification

Introduce a common model specification containing:

- Dependent variable.
- Independent variables.
- Input transformations.
- Output transformation.
- Basis functions or symbolic expression.
- Fitted parameters.
- Parameter constraints.
- Physical units.
- Loss definition.
- Solver configuration.

Distinguish transformations of the regression target from transformations of the predictors.

The model must permit fitting transformed observables while evaluating errors in the original physical observable.

## 6. Weighted fitting and uncertainties

Support:

- Unweighted residuals.
- Inverse-variance weighting.
- Explicit observation weights.
- Full covariance weighting in a future extension.

Validate that supplied uncertainties are positive and finite where required.

Preserve the distinction between statistical measurement uncertainty, estimated numerical error, and weighting introduced for scientific/modeling reasons.

## 7. Benchmark problems

Implement the following representative tests.

### Problem A — Linear in coefficients

Fit:

`y = a0 + a1*x1 + a2*x2^(-1/2)`

Compare against direct QR.

### Problem B — Multivariate polynomial

Fit:

`y = a0 + a1*x1 + a2*x2 + a3*x1*x2 + a4*x2^2`

Verify coefficient recovery and correct basis ordering.

### Problem C — Nonlinear exponents

Fit:

`y = a0 + a1*x1^a2*x2^a3`

Compare NonlinearSolve.jl and CurveFit.jl using multiple initial guesses.

### Problem D — Weighted fitting

Fit synthetic heteroscedastic data with known uncertainties.

Verify the weighted objective, parameter recovery, and residual calculations.

### Problem E — Ill-conditioned inputs

Use predictors with very different numerical scales and nearly dependent basis columns.

Compare raw and scaled fitting and verify solver diagnostics.

### Problem F — Symbolic discovery

Generate data from a known low-complexity expression.

Run a small symbolic search and verify that valid candidate models are returned.

Do not require a stochastic optimizer to discover one exact expression on every run.

## 8. Numerical validation

For every solver backend, record:

- Termination status.
- Final objective value.
- Iteration count where available.
- Residual norm.
- Parameter vector.
- Jacobian rank or conditioning diagnostics where available.
- Warnings.
- Solver version and configuration.

For nonlinear fitting, support repeated initial guesses when needed.

Do not assume solver convergence implies a globally optimal solution.

## 9. Reproducibility

Store:

- Training data IDs.
- Feature definitions.
- Target transformation.
- Loss definition.
- Fitting weights.
- Random seed.
- Solver name.
- Solver options.
- Package versions.
- Final fitted model.

Ensure saved candidate models can be reconstructed without executing arbitrary serialized source code.

## 10. Final decision report

Before implementing the full regression API, report:

1. Which solver libraries were tested.
2. Whether CurveFit.jl can serve as the unified fitting interface.
3. Any missing functionality.
4. Numerical agreement on the benchmark problems.
5. Numerical robustness and failure modes.
6. Approximate runtime and allocation comparisons.
7. Chosen dependency stack.

Favor correctness, stability, and simplicity over marginal speed improvements.

Do not build custom Gauss–Newton, Levenberg–Marquardt, or trust-region algorithms.

The final architecture must allow us to replace the numerical fitting backend without changing the public scientific API.

## 7. Final recommendation

For EmpiricalRelationsForge.jl, I would adopt this strategy:

Use `LinearAlgebra` for linear-in-parameters models

This covers polynomial fits, multivariate fits, and most of the fixed-functional-form empirical relations we have discussed.

Use `NonlinearSolve.jl` for nonlinear coefficient optimization

It provides the flexibility and specialized numerical methods needed for more general candidate formulas.

Use `SymbolicRegression.jl` for discovering mathematical structure

Let the search engine propose expressions; use the common validation framework to determine whether they are scientifically useful.

Implement our own scientific modeling and validation layer

This is where Forge can provide something the existing Julia ecosystem does not: convenient construction, discovery, and EOS-aware validation of interpretable scientific relations.

I would still test `CurveFit.jl` first because its unified interface is attractive and its current implementation is based on the same SciML nonlinear-solving ecosystem. But I would not build an entirely new regression numerical engine.

The novelty of Forge should lie in discovering physically meaningful equations, comparing functional forms, handling scientific metadata, and establishing whether a relation generalizes to unseen equations of state—not in reinventing least-squares optimization.
